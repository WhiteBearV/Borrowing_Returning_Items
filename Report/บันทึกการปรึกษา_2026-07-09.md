# บันทึกการปรึกษา รอบใหม่ — 9 กรกฎาคม 2569
**โปรเจค:** ระบบยืม-คืนอุปกรณ์ (Equipment Borrowing System)
**ผู้จัดทำ:** วีรภัทร สาลีผล

เอกสารนี้สรุปประเด็นที่อาจารย์ให้ความเห็น/ตั้งคำถามในรอบนี้ พร้อมผลการตรวจสอบจากระบบจริง
และแนวทางดำเนินการ เพื่อใช้ประกอบการปรึกษา

## ประเด็นที่ 1 — ความเข้ากันได้ของฐานข้อมูลอื่น (ถ้า PostgreSQL เสีย ย้ายไป MySQL ได้ไหม)

**คำถามอาจารย์:** ระบบเราเอารูปใส่เข้า DB เลยหรือเปล่า ถ้า Postgres เสียแล้วย้ายไป MySQL จะยังใช้ได้ไหม

**ผลตรวจสอบจากโค้ดจริง:**
- ระบบ **ไม่ได้เก็บรูปลงฐานข้อมูล** — รูปทุกชนิด (รูปอุปกรณ์ / รูปความเสียหาย / รูปโปรไฟล์)
  ถูกบันทึกเป็น **ไฟล์บนดิสก์** ที่โฟลเดอร์ `./uploads/` แล้ว DB เก็บไว้แค่ **ข้อความ path**
  เช่น `/uploads/<uuid>.jpg`
  - อ้างอิง: `equipment_service.py` (`save_image()` → เขียนไฟล์ลง `UPLOAD_DIR`, คืน path)
  - `models/user.py` (`avatar_url` เป็น `String`), `models/borrow_item.py` (`damage_photo_urls` เป็น list ของ path)
- ดังนั้นเรื่อง "รูป" ไม่ผูกกับชนิดฐานข้อมูลเลย ย้าย DB ได้โดยไม่กระทบรูป

**สรุปเรื่องย้าย Postgres → MySQL:** ทำได้ แต่มี 3 จุดที่ต้องแก้ (ไม่ใช่รูป):
1. **JSONB** — คอลัมน์ `damage_photo_urls` และ audit log ใช้ชนิด `JSONB` ของ Postgres
   MySQL 8 ใช้ `JSON` (ต่างชื่อ/พฤติกรรมเล็กน้อย)
2. **UUID** — Postgres มี native UUID, MySQL ต้องเก็บเป็น `CHAR(36)` หรือ `BINARY(16)`
3. **Driver** — ต้องเปลี่ยน `asyncpg` → `asyncmy`/`aiomysql` และแก้ `DATABASE_URL`

> **ข้อสังเกต:** ตัวระบบใช้ SQLAlchemy 2.0 (ORM) เป็นหลัก ซึ่งรองรับหลายฐานข้อมูลอยู่แล้ว
> ความเสี่ยงจริงจึงจำกัดอยู่ที่ชนิดข้อมูลเฉพาะ Postgres ข้างต้น ไม่ใช่ทั้งระบบ
> **แนวโน้มความเห็น:** คงใช้ PostgreSQL ต่อ (เสถียร + รองรับ JSONB/UUID ตรงกับดีไซน์)
> ส่วนการกัน "Postgres เสีย" ควรแก้ด้วย **backup/restore + volume สำรอง** มากกว่าเปลี่ยนยี่ห้อ DB

**ต้องการคำยืนยันจากอาจารย์:** ต้องการให้รองรับ MySQL เป็นทางเลือกจริงจัง (ต้องทดสอบเพิ่ม)
หรือแค่ยืนยันว่า "ย้ายได้ถ้าจำเป็น" ก็พอ

## ประเด็นที่ 2 — การนำสินค้าเข้าคลังต้องเห็นว่าเอาอะไรเข้าบ้าง (มีเอกสารประกอบ)

**ความเห็นอาจารย์:** ตอนนำอุปกรณ์เข้าคลัง ควรมีเอกสารให้เห็นว่านำอะไรเข้าบ้าง

**สถานะปัจจุบัน:** ตอนสร้างอุปกรณ์มี audit log บันทึก action `create equipment` แล้ว
แต่ **ยังไม่มี "เอกสารรับเข้า" (ใบนำเข้า/ร่างเข้า)** ที่รวมรายการหลายชิ้นในการนำเข้าครั้งเดียว
พร้อมแนบใบสั่งซื้อ/ใบเสร็จ (ตรงกับ advisor #2 เดิมที่ยังค้าง)

**แนวทางดำเนินการ:** เชื่อมกับประเด็นที่ 3 — ทำเป็น "เอกสารร่างเข้า" (ดูด้านล่าง)

## ประเด็นที่ 3 — เอกสาร ร่างเข้า / ร่างออก / ร่างยืม / ร่างคืน (สำคัญมาก)

**ความเห็นอาจารย์:** ควรมีเอกสาร ร่างเข้า–ร่างออก–ร่างยืม–ร่างคืน ได้แล้ว และเห็นชัดเจน

**สถานะปัจจุบัน:**
| เอกสาร | มีแล้ว? | หมายเหตุ |
|---|---|---|
| ร่างยืม (ใบยืม PDF) | ✅ **เสร็จ** | สร้าง PDF ใบยืมได้ + **ปุ่ม "ดูตัวอย่างใบยืม" preview ก่อนกดส่งคำขอ** (advisor #3) — `POST /borrow-requests/preview-pdf` |
| ร่างคืน (ใบรับคืน/สรุปผล) | ✅ **เสร็จ** | `GET /borrow-requests/{id}/return-pdf` — สรุปสภาพเมื่อคืน (ปกติ/เสียหาย/สูญหาย/ใช้หมด ฯลฯ) + วันที่รับคืน + ช่องลายเซ็นผู้รับคืน; ปุ่มในหน้าคำขอที่ completed (ทั้ง นศ.+admin) |
| ร่างเข้า (ใบรับเข้าคลัง) | ❌ ยังไม่ทำ | ตรงกับประเด็นที่ 2 — ต้องสร้าง data model รับเข้าใหม่ |
| ร่างออก (ใบปลดระวาง/นำออก) | ❌ ยังไม่ทำ | ปัจจุบันปลดระวาง (retire) ยังไม่เก็บเหตุผล/ผู้รับผิดชอบ และไม่ออกเอกสาร |

> **ความคืบหน้า 9 ก.ค.:** ทำ ร่างยืม preview + ร่างคืน เสร็จแล้ว (reuse `pdf.py` — `_build_doc(req, kind)`
> รองรับ borrow/preview/return). เหลือ ร่างเข้า/ร่างออก ซึ่งต้องเพิ่ม data model/field ก่อน

**แนวทางดำเนินการ (เสนอ):** ทำ 4 เอกสารเป็น PDF จาก ReportLab (มีของเดิมใช้ซ้ำได้) รูปแบบเดียวกัน
- **ร่างเข้า:** เลขที่เอกสาร, วันที่, ผู้รับเข้า, รายการ+จำนวน, แนบเลขใบสั่งซื้อ/ใบเสร็จ
- **ร่างออก:** เลขที่, วันที่, เหตุผลปลดระวาง, ผู้อนุมัติ, รายการ
- **ร่างยืม:** ต่อยอดใบยืมเดิม + เพิ่ม preview ก่อนกดส่ง (advisor #3)
- **ร่างคืน:** สรุปสภาพคืน (ok/damaged/lost ฯลฯ) + แนบรูปความเสียหาย + ผู้รับคืน

**ต้องการจากอาจารย์:** ตัวอย่างแบบฟอร์มเอกสารของคณะ (ถ้ามี) เพื่อทำ layout ให้ตรงของจริง

## ประเด็นที่ 4 — เลขครุภัณฑ์ในระบบไม่ตรงกับเลขจริง ✅ (แก้เสร็จแล้ว 9 ก.ค.)

> **สรุปสถานะ:** DB dev ตอนนี้มีครุภัณฑ์ **704 ตัวใช้เลขทะเบียนจริง** (คณะ `63-/64-/65-/66-/67-...`,
> พระราชทานใช้รหัสใหม่ `สนว.-...`) จัดหมวดตามคีย์เวิร์ดครบ. รายการนอกทะเบียนแยกเป็น
> **วัสดุใช้ซ้ำ (material) 540** + **วัสดุสิ้นเปลือง (consumable) 3** เก็บเลข Snipe-IT เดิมไว้.
> เหลือ **34 รายการ "ตกทะเบียน"** (สว่าน/Cisco/Apple TV/webcam/จอ 27"/AP) พักเป็น material
> ในหมวด "ไม่ระบุหมวดหมู่" — **รอถามอาจารย์ว่าเป็นครุภัณฑ์ (ต้องออกเลขทะเบียน) หรือวัสดุถาวร**.
> สคริปต์ทำซ้ำได้: `import_register.py`, `seed_equipment.sql`, `reclassify_consumable.sql`,
> `remap_durable_codes.sql`, `reclassify_material.sql`. ไฟล์เทียบ: `Report/เทียบทะเบียน-vs-DB.md`.

**ความเห็นอาจารย์:** เลขที่เราใส่กับเลขจริงไม่ตรงกัน ให้ตรวจกับไฟล์ทะเบียนคุมทรัพย์สิน

**ผลตรวจสอบ (เทียบ seed data กับไฟล์ Excel ทะเบียนคุมทรัพย์สิน 4 พ.ย. 2568):**

ยืนยันว่า **เลขไม่ตรงจริง** — เลขในระบบเป็นเลขจากระบบเดิม (Snipe-IT) ไม่ใช่เลขครุภัณฑ์ทางการ

| | เลขในระบบตอนนี้ (seed) | เลขจริงในทะเบียน |
|---|---|---|
| รูปแบบ | ตัวเลข 5–6 หลัก เช่น `111001`, `111040` | `63-213-001-001-0001` (คณะ) / `สนว.-65-201-...` (พระราชทาน) |
| จำนวน | 1,103 รายการ (ทั้งหมดเป็นเลข Snipe-IT) | 543 รายการทางการ (คณะ) + ชุดพระราชทานอีกชีต |
| ตัวอย่าง | `111001` = Dell Optiplex 7040 SSF | `63-213-001-001-0001` = คอมพิวเตอร์ตั้งโต๊ะ Dell Optiplex 7040 SFF |

**สาเหตุ:** ไฟล์ seed มาจาก export ของ Snipe-IT (ระบบเดิม) จึงติดเลข internal ของ Snipe-IT มา
ไม่ได้ mapping กับเลขครุภัณฑ์ในทะเบียนคุมทรัพย์สินของคณะ

**แนวทางแก้:**
1. เขียน mapping ชื่อรายการ → เลขครุภัณฑ์จริง จากไฟล์ Excel (มี 47 ชนิด แยกตามช่วงเลข)
   - เช่น Dell Optiplex 40 เครื่อง → `63-213-001-001-0001` ถึง `-0040`
2. แก้ `backend/scripts/import_equipment.py` ให้ import จากไฟล์ทะเบียนจริง ใช้คอลัมน์
   `รหัสครุภัณฑ์` เป็น `equipment.code` (แทนเลข Snipe-IT)
3. สร้าง seed ใหม่แล้ว re-seed DB

**ประเด็นที่ต้องถามอาจารย์:**
- ชีต "ครุภัณฑ์ที่ได้รับพระราชทาน" มีทั้ง **รหัสเดิม / รหัสใหม่ (สนว.-...)** และหลายแถวหมายเหตุ
  ว่า *"ไม่พบเลขครุภัณฑ์"* → จะใช้เลขไหนเป็นหลัก และรายการที่ไม่มีเลขจะจัดการอย่างไร
- รายการวัสดุสิ้นเปลือง (ไม่มีเลขครุภัณฑ์ในทะเบียน) จะให้ระบบออกรหัสภายในเองไหม
