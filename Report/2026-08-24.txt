### Backend

- **`app/services/auth_service.py` — `verify_email`**: token ที่ถูกใช้ไปแล้ว (กดลิงก์ยืนยันซ้ำจากอีกอุปกรณ์/แท็บ) เดิม error "Invalid or expired token" ทั้งที่บัญชียืนยันสำเร็จไปแล้วจริง แก้ให้ถือเป็นสำเร็จซ้ำได้ (idempotent) — token ที่ไม่มีอยู่จริงเท่านั้นถึง error
- **`app/services/borrow_service.py` — `create_request`**: บั๊กจริงที่พบจากการทดสอบ — ปิดใช้งาน/ปลดระวางหน่วยแรก (รหัสต่ำสุด, ตัวแทนกลุ่ม) ของอุปกรณ์รุ่นที่มีหลายหน่วย (เช่น Arduino UNO R4 ที่ยืมได้หลายชิ้น) ทำให้ยืมทั้งรุ่นไม่ได้เลยแม้หน่วยอื่นยังว่างอยู่ — สาเหตุคือเช็คสถานะของหน่วยตัวแทนก่อนรู้ด้วยซ้ำว่ามีกลุ่ม แก้ให้เช็คสถานะเฉพาะกรณีมีหน่วยเดียวจริง ๆ ส่วนรุ่นที่มีหลายหน่วยให้สแกนหาหน่วยว่างในกลุ่มเหมือน `approve_request` ที่ทำถูกอยู่แล้ว
- **`app/services/borrow_service.py` — `return_item`**: พบต้นตอบั๊ก "อุปกรณ์ขึ้นสถานะพร้อมทั้งที่ของเหลือ 0 ชิ้น" (เช่น `212001 0/1 พร้อม`) — ไม่เคย sync `equipment.status` ตอนคืนของสภาพเสียหาย/สูญหาย มีแต่ลด `quantity_available` ถาวรเฉย ๆ แก้ให้หน่วยเดียว (`quantity_total=1`) คืนสภาพ `damaged`/`discarded` → status เป็น `damaged`, คืนสภาพ `lost` → status เป็น `unavailable` (ตรงกับ label เดิมของ `import_service` "สูญหาย/เสื่อมสภาพ") — ก้อนวัสดุ `quantity_total>1` ที่ยังไม่แยกรายชิ้นไม่แตะ status เพราะเสียแค่หน่วยเดียวไม่ได้แปลว่าทั้งก้อนเสีย (ตรง CLAUDE.md §5 เงื่อนไข condition_on_return)
- **`app/services/equipment_service.py`**: เพิ่ม `is_currently_borrowed` (คำนวณจาก `borrow_items` จริง ไม่ใช่ derive จากช่องว่าง `quantity_available`/`quantity_total` ที่ลองแล้วผิด — ของเสีย/สูญหายที่คืนไปแล้วก็มีช่องว่างค้างถาวรได้เหมือนกัน ไม่ได้แปลว่ามีคนถือของอยู่จริง) รวม `_borrowed_equipment_ids` เดิม (แค่ set id) กับ `get_holders` เดิม (query แยก) เป็น `get_holders_map` เดียว — ได้ทั้ง "ถูกยืมอยู่ไหม" และ "ใครถือ" (ชื่อ + รหัสนักศึกษา) ในคิวรีเดียว ใช้กับทั้ง `list_equipment`, `list_equipment_grouped`, `get_equipment_group_detail`
- **`app/schemas/equipment.py`**: เพิ่ม `HolderInfo.student_number`, `EquipmentResponse.is_currently_borrowed`/`holder`, `EquipmentUnitSummary.is_currently_borrowed`/`holder` — ย้าย `HolderInfo` ขึ้นไปนิยามก่อน `EquipmentResponse` (แก้ forward-reference)
- **`app/schemas/equipment.py` — `EquipmentBulkUpdate`**: เพิ่ม `name`/`item_type`/`category_ids` เข้าไปในฟิลด์ที่แก้พร้อมกันหลายรายการได้ (ตามคำขอ "แก้หลายชิ้นให้เหมือนแก้ทีละชิ้น") — `code`/`serial_number` ยังตัดออกเหมือนเดิมเพราะ unique constraint (ตั้งค่าเดียวกันหลายแถวพัง), `quantity_total`/`quantity_available` ตัดออกเพราะเป็นตัวนับสต็อกต่อหน่วย
- **`app/services/equipment_service.py` — `bulk_update_equipment`**: เพิ่ม logic แยก `category_ids` ออกจาก setattr loop (relationship ต้อง resolve ผ่าน `_resolve_categories` แทน) + normalize ชื่อผ่าน `_normalize_name`
- **`app/routers/equipment.py`**: ปรับ endpoint `/equipment/{id}` ให้เรียก `get_holders_map` ใหม่แทน `get_holders` เดิม

### Frontend

- **`components/common/Tooltip.jsx`**: บั๊กจริงที่พบและ repro ได้ในเบราว์เซอร์ — tooltip แบบ `position: absolute` เดิมอยู่ในตารางที่มี `overflow-x-auto` (หน้าจัดการอุปกรณ์) พอ hover ปุ่ม "?" ตรง "แยกเป็นรายชิ้น" bubble ที่โผล่ออกมาดันความกว้างตารางจนเกิด scrollbar แนวนอน ทำให้แถวขยับ ปุ่มเลื่อนหลุดจากใต้ cursor → `mouseleave` ยิง → bubble หาย → scrollbar หาย → ปุ่มเลื่อนกลับมา → `mouseenter` ยิงใหม่ วนซ้ำไม่หยุด (วัดจริงด้วยการติด event listener: **1,792+ event ใน 3 วินาที**) แก้ด้วยการ portal bubble ไป `document.body` แบบ `position: fixed` คำนวณตำแหน่งจากจุดจริงของปุ่ม (แพทเทิร์นเดียวกับที่ `NotificationBell.jsx` เคยแก้ปัญหา sidebar ตัดขอบมาก่อน) — ทดสอบซ้ำเหลือ 1 enter, 0 leave ไม่กระพริบแล้ว
- **`pages/VerifyEmailPage.jsx`**: เพิ่ม `useRef` กัน React StrictMode ยิง API ยืนยันอีเมลซ้ำตอน dev (token ใช้ได้ครั้งเดียว โดนยิงซ้ำแล้วพัง)
- **`pages/RegisterPage.jsx`, `pages/admin/UsersPage.jsx`**: แก้ประกอบ `full_name` เดิมต่อคำนำหน้ากับชื่อตรง ๆ ไม่มีช่องว่าง ("นายวีรภัทร" ควรเป็น "นาย วีรภัทร") เพิ่มช่องว่างให้ถูก
- **`pages/admin/BorrowRequestsPage.jsx`**: แก้จอกระพริบตอน poll พื้นหลังทุก 4 วิ — เดิม `setLoading(true)` ทุกรอบทำทั้งหน้าสลับไป "กำลังโหลด…" แล้วกลับมา แก้ให้ poll พื้นหลังไม่โชว์ loading state (poll ยังทำงานเหมือนเดิม แค่ไม่รีเซ็ตหน้าจอ)
- **`pages/admin/AllBorrowsPage.jsx`**: เพิ่มตัวเลือก "เกินกำหนด" เข้าไปในดรอปดาวน์สถานะเดิม (ตอนแรกทำเป็น checkbox แยก ผู้ใช้ขอให้รวมเข้าดรอปดาวน์เดิมแทน) — backend มี `overdue_only` param รองรับอยู่แล้ว ไม่ต้องแก้ backend
- **`pages/admin/EquipmentManagePage.jsx`**: (1) แก้ status badge ต่อหน่วยให้ derive "ถูกยืม" จาก `is_currently_borrowed` จริงแทนการเดาจากช่องว่างสต็อก (2) เพิ่ม `BulkEditModal` ฟิลด์ ชื่ออุปกรณ์/ประเภท/หมวดหมู่ (หมวดหมู่แทนที่ของเดิมทั้งหมด มีข้อความเตือนในฟอร์ม) (3) โชว์ชื่อ+รหัสนักศึกษาผู้ยืมใต้ badge "ถูกยืม" ทั้งแถวหน่วยเดียวและแถวย่อยในกลุ่ม

## หมายเหตุ / ความเสี่ยง ⚠️

- **Audit log**: การแก้ข้อมูลตรง ๆ ผ่าน SQL วันนี้ (เว้นวรรคชื่อ 37 คน, backfill สถานะ 8 หน่วย, ลบขยะเทสต์ 20 แถว) **ไม่ได้ผ่าน `audit_service.log_action`** เพราะเป็นการแก้นอกระบบ ไม่ใช่ action ผ่าน UI/API ปกติ — ผิดหลัก CLAUDE.md §5 "ทุก action ของ admin ต้องเรียก audit_service.log_action" ในทางเทคนิค (ไม่ใช่ admin action แต่เป็น data hygiene ของทีมพัฒนา) ควรพิจารณาว่าจะบันทึกร่องรอยการแก้เหล่านี้ไว้ที่ไหนสักที่เพื่อความโปร่งใสในอนาคต
- **ประวัติการคืนของที่ถูกลบ**: ฟีเจอร์ "ลบประวัติการยืม" (`delete_request`) ลบ `BorrowItem` ทิ้งโดยไม่กระทบ `equipment.quantity_available`/`status` (ถูกต้องแล้วในแง่ข้อมูล) แต่ทำให้ตรวจสอบย้อนหลังไม่ได้ว่าของที่ค้างสต็อกหายไปเพราะอะไร — เป็น trade-off ที่ควรรู้ไว้ ถ้าอยากให้ตรวจสอบย้อนหลังได้ควรพิจารณา soft-delete แทน hard-delete ในอนาคต (ไม่ใช่เรื่องด่วน)
- **เทสต์รั่วข้อมูลลง DB จริง**: ยืนยันแล้วว่าเกิดขึ้นจริงวันนี้ 20 แถว ทั้งที่ pytest รายงาน "ทุกตัวผ่าน" — เป็นสัญญาณว่า cleanup logic ในบางไฟล์เทสต์ไม่น่าเชื่อถือ 100% ควรรีวิวก่อนรันเทสต์ทั้งชุดถี่ ๆ บน DB dev จริงต่อไป (ตรงกับที่เคยเจอปัญหานี้มาก่อนแล้วครั้งหนึ่งตามที่บันทึกไว้ในโค้ดคอมเมนต์ของหลายไฟล์เทสต์)
